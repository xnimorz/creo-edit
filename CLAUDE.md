# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `bun run build` — runs `build.ts` (Bun bundle to `dist/index.js` ESM, then `tsc -p tsconfig.build.json` to emit `.d.ts`).
- `bun test src/` — runs the suite. Tests live in `src/**/__tests__/*.spec.ts`. Each test file explicitly `import "./setup"` (or `../__tests__/setup`) to install happy-dom globals — there is no global preload, so a new test file must do the same.
- Single file: `bun test src/__tests__/caret.spec.ts`. Single test: `bun test --test-name-pattern "<name>"`.
- `bun run typecheck` — `tsc --noEmit -p tsconfig.json`.
- `src/__perf__/` holds perf-style specs that also run under `bun test`.
- `bun run release` — `scripts/publish.ts`: releases the packages that have something to release, editor first. A package goes out if its version is not on npm, or if what it ships has CHANGED since that version was released — decided from git: the release is the commit that last touched the version line of its `package.json`, and tests do not count. A changed package needs a new version, which the script sets (asked for in a terminal, or `--bump minor` / `--bump creo-edit=minor`; it suggests the smallest bump the other packages' ranges allow), renaming the changelog's `## Unreleased` to it and committing the bump locally under the version as the message — after the checks, before the upload. Everything is checked and built before anything is uploaded. `--dry-run` does all of it without uploading and puts the working tree back. It refuses to publish a package whose range on a sibling nothing on npm or in the run satisfies. The pure parts are in `scripts/release-lib.ts`, tested by `src/__tests__/releaseScript.spec.ts`.

`creo` is declared as a peer-dep (`>=0.2.9`); the published package has no other runtime deps.

`bunfig.toml` sets the test root to `src/`: `bun test src/` filters by substring, and `packages/mermaid/src/` would match it too.

## Architecture

**Two independent stores.** `docStore: Store<DocState>` holds the document; `selStore: Store<Selection>` holds the cursor/range. They are deliberately separate so caret motion does not dirty document subscribers and vice versa. Every command function takes `{ docStore, selStore }` and mutates whichever stores it needs.

**Controlled `contentEditable`.** The editor root is `contenteditable="true"` (or `"false"` — see read-only below). The browser owns selection rendering, IME composition, and the OS context menu (long-press / right-click). The model is held canonical by intercepting every `beforeinput` event in `input/nativeInput.ts`, calling `preventDefault()`, and dispatching the equivalent editor command. The browser is allowed to mutate the DOM in only one situation — during an active IME composition — and we reconcile on `compositionend` by diffing the affected scope's `textContent` against the pre-composition snapshot.

**Anchor ↔ DOM mapping.** `dom/anchorMap.ts` exposes `domToAnchor(node, offset, root)`, `anchorToDom(anchor, root)` and the batch `anchorsToDom(anchors, root)`. The mapper is pure DOM — it walks `data-block-kind` (only the outer block container has it; cells share their parent's `data-block-id`) and descends into `data-cell` / `data-col` for table / columns cells. Editor root is the only place these attributes are produced, by the views in `render/blocks/`.

The character walks in `plugin/anchorCodec.ts` (`visibleTextLength`, `visibleTextOf`, `offsetWithinScope`, `findTextPoint`, `findTextPoints`) are the hottest code in the library — anchor path, IME path, selection path — so they iterate `firstChild`/`nextSibling` and never allocate per node visited.

`anchorsToDom` exists because a range-decoration repaint resolves two anchors per range and thousands of ranges per frame: it looks the block element up once per block id and hands each block's whole batch to `AnchorCodec.anchorsToDom` (optional; falls back to per-anchor). `codeBlockCodec` implements it by sorting on offset and walking each line once for all the anchors on it.

**Code-block anchors are O(log lines).** `CodeBlockView` publishes each line's model start offset as `data-line-start` (`LINE_START_ATTR`), so `codeBlockCodec.anchorToDom` binary-searches `blockEl.children` and then walks only the found line, and `domToAnchor` reads the owning line's attribute instead of summing every line above it. Both were O(lines × nodes) before, which made a syntax-highlighting repaint quadratic in file size. The attribute is additive — a host rendering its own code view without it still resolves, through the linear fallback still present in both functions.

**Selection sync.** `nativeInput.ts` keeps Anchor and native `Range` aligned with two coordination devices: a `programmaticSeq`/`lastObservedSeq` echo guard (skips the `selectionchange` event the browser fires after our own programmatic write), and a `renderPending` window cleared on the next animation frame after a docStore mutation (the renderer replaces text nodes for the changed block, native selection collapses onto detached nodes, and the second `selectionchange` would corrupt selStore without this).

**Block model** (`model/types.ts`). `DocState = { byId: Map<BlockId, Block>; order: BlockId[] }` where `order` is sorted by each block's `index: FracIndex` — a base-62 fractional key so insert-between is O(log n) with no renumbering (`model/fractional.ts`). `attachAutoRebalance` runs a microtask check after each mutation and rebalances only when a key has outgrown the soft threshold. Block kinds: `p`, `h1..h6`, `li` (with `ordered`/`depth`), `code` (multi-line monospaced; Enter inserts `\n` instead of splitting), `img`, `table`, `columns`. `isTextBearing()` (`model/blockText.ts`) is the canonical predicate for "block has a top-level `runs: InlineRun[]` field". It is **registry-driven** (`plugin/textBearing.ts`), mirroring `BlockDef.isTextBearing` at install time — a hard-coded list of the nine built-ins meant `setBlockType` / `splitBlock` / `mergeBackward` / `toggleMark` refused plugin text blocks, so Enter inside a plugin `task` block did nothing. When the flag is omitted it is inferred: atomic → false, a block shipping its own `runsAt` addresses nested slots → false, otherwise true. The predicate still confirms `runs` exists at runtime, so a mis-declared flag degrades rather than throws.

**Anchors** are `{ blockId, path: number[], offset }`. Path encoding by block type:
- text-bearing (`p`/`h*`/`li`/`code`): `[charOffset]`
- `table`: `[row, col, charOffset]`
- `columns`: `[colIndex, charOffset]`
- `img`: `[side]` where `side` is 0 (before) or 1 (after)

`runsAt(block, anchor)` (`model/cellAccess.ts`) is the canonical way to walk into the right runs slot regardless of block kind — prefer it over hand-rolled path indexing.

**Inline runs** carry `text`, optional `marks`, and optional `attrs: { class? }`.

`marks` is a `ReadonlyMap<MarkName, MarkAttrs>` — name → payload, `null` for the five boolean marks, `{ href, title? }` for `link`. It is a map rather than a set because a set of strings has nowhere to put an href, and encoding one into the key makes every lookup a scan. Helpers live in `model/marks.ts` (`hasMark`, `markAttrs`, `withMark`, `marksOf`, `marksEqual`, `linkHref`); `marksEqual` runs once per adjacent run pair inside `normalizeRuns` on every keystroke, so it early-outs on identity and size. Wire form is `{ name: attrs }`; the legacy `string[]` form is accepted on read (`model/runSerialize.ts`) and never written.

**Mark registry** (`plugin/markRegistry.ts`). One `MarkDef` per mark name — wrapping `tag`, `domAttrs(attrs)`, `matchHTML` tags + `parseHTML`, markdown syntax, and `order` (lower wraps closer to the text; fixed so toggling never reshuffles the DOM under a run). `InlineRunsView`, `clipboard/inlineHtml.ts` (parse + serialize) and `markdown/serialize.ts` all walk it — each of those used to carry its own hard-coded five-mark table. Plugins add marks via `EditorPlugin.marks`. The link mark's href is sanitized (`safeHref`) on the way **into the DOM only**, so `toJSON()` hands the host back exactly what it stored.

`attrs` is view-only derived styling (syntax tokens, spell-check) rendered onto the run's span: it does not serialize, is orthogonal to mark toggling, and blocks run merging so token boundaries survive `normalizeRuns`. Any code re-slicing a run must go through `withRunText(run, text)` (`model/blockText.ts`) so marks *and* attrs ride along.

**Commands and history.** `createEditor.dispatch(cmd)` is the single mutation entry point and returns `boolean` ("did it apply"). It calls `history.record(tag)` *before* applying the command; matching tags coalesce into one undo step (`textCommands` insert/deleteBackward/deleteForward use `text:insert`, `text:deleteBack`, `text:deleteFwd` so consecutive typing collapses, and IME composition reuses `text:insert` so a multi-char composition is one undo). Which tags coalesce comes from `Registry.shouldCoalesce` — `createHistory` takes the registry as its policy, so `EditorPlugin.historyCoalescePrefixes` actually has an effect.

**Nothing may mutate `docStore` outside a command.** A direct `docStore.set()` emits no `DocChange` (so anything persisting off `onChange` silently drops the edit) and pushes no history entry (so it isn't undoable). `dragHandlePlugin` and `addBlockPlugin` did exactly that and lost both; they now dispatch. `commands/blockCommands.ts` holds the structural ops — `moveBlock`, `insertBlocks`, `removeBlocks`, `replaceBlocks` — which double as the targeted-update path for changes arriving from outside on the same document. `setDoc` is a replacement and can't preserve identity, caret, undo or per-block changes; reach for those instead.

**`CommandCtx`** carries `dispatch`, `change` (record a `DocChange`) and `editor` alongside the two stores, so a plugin command composes with built-ins rather than reimplementing them. `editor.commandCtx` is the same object, for toolbar buttons and menu items. New commands live under `src/commands/<group>Commands.ts` and are wired into the `Command` union and `dispatch` switch in `createEditor.ts` — and into `BUILTIN_COMMANDS` there, which the read-only gate reads.

**Read-only.** `EditorOptions.editable` (`boolean | (() => boolean)`, default true) is honoured in *two* places, because `dispatch()` is public and the attribute alone would not stop a plugin: the root's `contenteditable`, and the dispatcher. Mutating commands return `false` before `history.record`, so no empty undo steps accumulate. Plugin commands are gated inside `Registry.runCommand` and opt back in with `CommandDef.readOnlySafe` (the cells plugin's navigation commands do). Host-level document APIs (`setDoc`, `appendBlocks`, …) are deliberately NOT gated — that's how a read-only viewer loads content.

**Change stream and position mapping** (`model/changes.ts`). Commands emit `DocChange`s into an ambient collector (`recordChange` / `recordTextChange`); `dispatch` opens the collector with `collectChanges` and hands the batch to `editor.onChange` subscribers. Nested dispatches fold into one flat batch and only the outermost emits. `mapAnchor(anchor, changes, bias)` moves an externally-held anchor (review comment, diagnostic, bookmark) through an edit, returning `null` when the position no longer exists. Variants: `text` (with a `container` path so table cells are addressed separately), `split`, `merge`, `insertBlock`, `removeBlock`, `resetBlock` (unmappable internal reshape — table row/col ops), `moveBlock`, `format` (a mark toggled over a span), `blockAttrs` (`setBlockType`, list indent/outdent), `replaceDoc` (carrying a `reason`: setDoc / setDocFromHTML / undo / redo). The last three move no character, so `mapAnchor` passes anchors through — they exist so the stream is a complete op log for consumers that persist rather than map. A new mutating command must emit, or anchors silently drift and persisted documents silently lose the edit.

**Render layer.** `render/DocView.ts` is the keyed reconciler over `doc.order`. Block immutability + identity-based `shouldUpdate` makes per-keystroke render cost O(1) blocks — only the touched block re-renders. `CodeBlockView` extends the same trick *inside* a block: it memoizes its per-line run split against the previous one and hands back the previous line's array reference wherever the line is unchanged, so `InlineRunsView`/`RunView`'s identity guards skip it. Line keys ride along with that memo (unchanged prefix and suffix keep theirs) rather than being array indices, so inserting a line at the top doesn't renumber everything below it. `render/blocks/` contains one view per block type. Each block element emits `data-block-id` and `data-block-kind` for the anchor map; cells inside `table`/`columns` emit `data-cell="r:c"` / `data-col="c"`. Image blocks emit `contenteditable="false"` so the native caret skips over them.

**Input pipeline** (`input/nativeInput.ts`). `attachNativeInput(root, stores, options)` wires:
- `selectionchange` (document-level) → Anchor → `selStore`
- `selStore` change → native Range, synced post-render via rAF
- `beforeinput` → `preventDefault` + dispatch command (most `inputType`s map directly; `deleteContentBackward`/`deleteContentForward` route through `handleBackspace`/`handleDelete` which choose between within-block delete, block merge, or `deleteSelectedImage`)
- `compositionstart`/`end` → snapshot model length, diff DOM textContent on end, dispatch one `text:insert`
- `keydown` → `matchKeymap` chord → command (Tab routes to `tableNextCell` inside tables, `indentList` outside)
- `copy`/`cut`/`paste` on root → existing `clipboard/` modules (parser, serializer, image-file path)

**Virtualization** (`virtual/`). When `virtualized` is true (a boolean, or a thunk read at each render of the root), `VirtualDoc` mounts only blocks intersecting `[scrollTop − overscan, scrollTop + viewport + overscan]`; `HeightIndex` is a Fenwick tree of per-block heights for O(log n) viewport resolution. The host page must provide a scroll container. `editorId` must be passed (createEditor does) — without it the root resolves to "the first editor in the document", which is the wrong one as soon as a page holds two. What it takes to be right in a real host, each of which was a bug found in cront.app: a block's height is its **advance** (the distance to the top of what is laid out next, so margins count), measured in one pass and **kept by block id** (the index is rebuilt with `HeightIndex.from` when `order` or the hidden set changes — never `resize`d, which attached heights to whichever block took the index); the window is placed from **where the root is in its scroller** (`syncRel`), and only the root's **own** blocks are measured (`owns` — a nested editor's are its own); **pins** (`pinnedIndices`: the selection's ends and the focus block's neighbours while the editor has the focus, the block holding the focused element, a pending `scrollToBlock`) are mounted outside the window with gap spacers, because unmounting them drops the browser's selection or focus; **`hidden`** blocks are skipped and take no height; consecutive `li` are **grouped** in one list keyed by the run's first block in the document, as `DocView` does; it **anchors the scroll itself** (`holdAnchor`: the first visible block put back after a measure or a render; `overflow-anchor: none` on `.creo-vroot`; a scroll position someone else moved is adopted, never "corrected"); and a scroll re-renders only once the viewport, with half a screen to spare, leaves what is mounted (`needsWindow`). In a headless DOM with no layout (`vroot` height 0) nothing is measured and the estimates stand — that is what the specs run on.

**Anything running per edit must be O(mounted), not O(document).** This is the invariant that makes "one block per source line" viable, and it is easy to break because iterating `doc.order` looks harmless. Known instances, all fixed and gated in `src/__perf__/lineBlocks.spec.ts`: `DecorationManager.sync` and `.position` take one `querySelectorAll` and iterate the mounted set (walking `doc.order` with a `querySelector` per block cost ~1.2s per sync at 50 000 blocks, on every keystroke); `attachAutoRebalance` skips its O(n) key scan unless `order` identity changed, which only an insert can do. Two costs remain O(document) by construction: `updateBlock` clones `byId` (0.42 ms at 50 000), and history pins one `DocState` per undo step — bounded by `HISTORY_MAX_BLOCK_SLOTS` rather than fixed, because 250 unbounded steps at 50 000 blocks grew the heap by 926MB. Both dissolve if `byId` becomes a persistent map or history entries become inverse patches.

**Sub-block virtualization** (`plugin/selfVirtualized.ts`). A `BlockDef` may declare `selfVirtualized: { measureHeight }`, meaning the block windows its own internal rows (a 5,000-line code block is one block, so block-level windowing does nothing for it). `VirtualDoc` then excludes it from `ResizeObserver` — matched by `data-block-kind`, tracked in `selfElByBlock` — trusts `measureHeight` even while the block is off-screen so scrollbar geometry is right from frame one, and passes a `BlockViewport { top, bottom }` in the block's own coordinate space down through the view props. The block owns its anchor codec's correctness across its own spacers, which is why the built-in code block does *not* opt in (`codeBlockCodec` walks every mounted `.ce-code-line`).

**Decorations** (`plugin/decorations.ts`). Per-block overlay UI in a sibling layer. `DecorationDef.targets(block, blockEl)` narrows the anchor to sub-elements (code lines → a per-line gutter); omitted, it defaults to `[blockEl]`, i.e. the original behaviour. `slotWidth` sizes the gutter slot; `uniformTargets` promises equal-height contiguous targets so `position()` takes one layout read per (def, block) instead of one per line. `targets()` is memoised per frame.

**Range decorations** (`plugin/rangeDecorations.ts`, `dom/highlights.ts`). `EditorPlugin.rangeDecorations` paints arbitrary, overlapping `AnchorRange`s through the CSS Custom Highlight API — zero DOM mutation, so nothing new for the character walk to account for. There is deliberately **no** DOM fallback; `editor.supportsRangeDecorations()` is the capability flag. `dom/highlights.ts` is the single place that touches `CSS.highlights` (the search plugin goes through it too).

One repaint asks *every* source for its ranges first, then resolves *all* their endpoints in a single `anchorsToDom` batch. Resolving per decoration made the cost scale with how many highlight names a host registers (a tokenizer bucketing into 64 of them hands each a thin scatter over the whole file, so nothing groups by line); pooled, the same endpoints arrive dense and each line is walked once. `editor.refreshRangeDecorations()` schedules on the next frame — `refreshRangeDecorationsSync()` is the escape hatch for callers that must see the paint before returning.

`DecorationViewport.windowIn(blockId)` gives a source the visible half-open character window inside one block, computed from `data-line-start` plus one rect read against the scroll container. `firstBlock`/`lastBlock` say nothing about a document that *is* one block, which is exactly the shape that needs scoping. `null` means "not measurable — return everything".

**Repaint triggers.** Doc store, the scroll container (`dom/scroll.ts` resolves the nearest scrollable ancestor — `scroll` doesn't bubble, so `window` is both deaf to the editor's own pane and noisy about the page's), `resize`, and `dom/mountSignal.ts`. That last one replaced a `MutationObserver` with `subtree: true`, which caught block mount/unmount under virtualization but also fired for every text node the renderer touched while typing. `VirtualDoc` now announces mount-set changes explicitly; a host doing its own windowing calls `notifyMountedBlocksChanged(root)`.

**Inline widgets** (`plugin/inlineWidgets.ts`). `EditorPlugin.inlineWidgets` places non-text content *within* a line (ghost text, inlay hints). A widget must be invisible to three things, each handled in exactly one place: the character-offset walk (`plugin/anchorCodec.ts` skips subtrees carrying `INLINE_WIDGET_ATTR` — a custom codec must too), the IME composition diff (`nativeInput.ts` reads the scope via `visibleTextOf`), and clipboard serialization (free — the serializer works from the model). The manager re-places widgets after each render because the renderer owns block DOM; it listens to doc/sel stores rather than a MutationObserver so it never observes its own writes.

**Clipboard / HTML** (`clipboard/`). `htmlParser.ts` → blocks for paste and `setDocFromHTML`; `htmlSerializer.ts` ← selection for copy/cut. `drop.ts` handles drag-and-drop including image upload via `opts.uploadImage`. The clipboard handlers themselves live in `nativeInput.ts` — the `clipboard/` modules are pure parse/serialize.

**Mobile.** `input/mobile.ts` — coarse-pointer detection (`isCoarsePointer()`) and `visualViewport` tracking. The latter exposes `--creo-vv-height` / `--creo-vv-top` as CSS custom properties so host pages can position floating UI above the soft keyboard, and scrolls the focused editor's caret into view when the keyboard covers it (`keepCaretVisible`). The scroll runs only for a focused, editable editor, only on viewport shrink (never on `visualViewport.scroll`, which iOS fires on every pan), and only if the caret was visible before. Each of these conditions fixes a scroll jump seen in cront.app. It measures the caret rect, not the block, and finds the scroller with `revealScroller` (`dom/scroll.ts`), which requires real vertical overflow and stops at clips. Native selection handles, the OS long-press menu, IME, and autocorrect are all delivered by the browser through the `contentEditable` root — no editor-side replacement needed.

**Reading text out.** `editor.toJSON()` is memoized on `docStore` identity (one serialization per document version, however many callers ask). `editor.getText(blockId?)` reads `runs` straight off the model via `blockTextOf` (`model/blockText.ts`) — cells joined by `\t` across and `\n` down, atomic blocks contributing nothing — and counts characters exactly the way anchors do. Hosts that hash the buffer or rebuild line starts every keystroke should use it rather than serializing.

**Perf gates** live in `src/__perf__/codeBlock.spec.ts`: a 2 000-line code block with 64 token decorations at ~6 ranges/line, timed on mount, repaint, keystroke, single-anchor resolution, and a viewport-scoped repaint. They stub `Range` as well as `CSS.highlights` — happy-dom's `setStart` walks the document to validate its boundary point, so one call is O(nodes) and an unstubbed repaint measures happy-dom rather than the editor. Budgets are ~5-10× measured so noise doesn't flake them while a structural regression overshoots by orders of magnitude.

**Editor handle on the DOM root** (`dom/editorRef.ts`). Decorations and block views are created by the renderer and receive an element, not an editor — so the editor publishes itself on its root (`root.__creoEdit`, unchanged property name) and they walk up via `closestEditor(node)`. One module owns it and it is typed as the real `Editor`; it used to be an untyped `any` with a hand-rolled structural type re-declared at each of four call sites. `focus` / `blur` / `scrollToBlock` use the root captured at mount, not `document.querySelector` — that returned null before mount and cannot cross a shadow boundary.

**Unknown block types round-trip** (`plugin/unknownBlock.ts`). A serialized block whose type has no codec is kept as an opaque non-editable block that re-emits its original JSON verbatim, rather than being dropped (which lost data permanently on the next save). First sight of the type registers a full passthrough kit — atomic codec, placeholder view, identity serialize codec. `EditorOptions.unknownBlocks` selects `"preserve"` (default) / `"drop"` / `"throw"`. Plugins install before deserialization, so a plugin that IS present always wins.

**Plugin lifecycle.** `onInit(editor)` runs after every plugin is installed (may return a teardown), `onDestroy(editor)` from `editor.destroy()`, `onPaste(ctx)` gets first refusal on the clipboard with all flavours pre-read (first `true` claims it), and `serializeDoc` / `deserializeDoc` wrap the block codecs for document-level metadata.

**A control inside a block** (`input/isolate.ts`). The root's `beforeinput` listener cancels everything that bubbles to it, so a field rendered inside a block has its typing swallowed unless it stops its own events first: `isolateInput(node)` stops the ten event types the input pipeline listens for. Add the field's own listeners BEFORE calling it (same node, registration order), and use `addEventListener` — creo delegates from the app root, above the editor, so a handler passed through creo props never fires for an isolated node. The other half is in `nativeInput.ts`: `applyNativeSelection` returns early while the focus is on anything inside a block that is not the editor's own text (`focusIsInsideABlock`), because writing the page's selection moves the focus to the editing host and would pull it out of the control that just dispatched a command — and, more broadly, whenever the editor does not have the focus at all (`hasFocus`): a document changed from outside must not take the caret from another field on the page. `editor.focus()` writes the model selection then (`writeSelection`). A keydown whose target is not the root or editable text is the control's: the keymap does not run (a block that wants the document's keys, like the mermaid canvas's ⌘Z, hands them on). An editor nested inside another's block is the inner one's alone: `ownNode` (nearest `[data-creo-edit]` is this root) gates reading the selection and the clipboard. Every key and input first reads the page's selection (`syncSelection`), since `selectionchange` arrives after a key that moved it.

**HTML block parsers are asked newest-first** (`plugin/htmlCodec.ts`). Built-ins install before plugins and the built-in `<pre>` parser never declines, so in registration order a plugin could not claim one kind of `<pre>`.

**Mermaid diagrams** (`packages/mermaid/`, published separately as `creo-edit-mermaid-plugin`; nothing in `src/` imports it). An atomic block, `{ type: "mermaid", source }`, with two modes switched on the block — Diagram and Code — held as view state in a per-editor runtime (`runtime.ts`), never in the document: a mode switch dispatches nothing, because the dispatcher snapshots for undo before ANY command runs and would leave an empty undo step. For the same reason the plugin's commands write the stores themselves rather than nesting dispatches (each nested dispatch is its own undo entry), and `mermaid.setSource` cannot avoid the entry for an unchanged source — callers check first.

- *Who draws what.* The creo view (`view.ts`) renders only the block's shell and declares no children, so the renderer leaves alone what `MermaidBlockUI` (`ui.ts`, plain DOM) builds inside it. Plain DOM because the engine replaces the canvas contents on every draw, and because of the delegation point above.
- *Engine.* Pele, behind `MermaidEngine` (`engine.ts`). `mount` must be synchronous once a diagram type's chunk is loaded — a block scrolled back into a virtualized window needs its real height on first measure — which is why the runtime keeps each lazy load as a value as well as a promise.
- *Visual editing* (`visual.ts`, `kits.ts`). The source is the only thing stored; a gesture becomes an operation, visimer compiles it to a minimal text edit, and the picture is redrawn. A kit per diagram type maps Pele's SVG to visimer's entities: nodes by `data-id`, edges BY ORDER (the two libraries number a repeated edge differently). Two parsers read the same language, so an edit Pele cannot draw is not applied (`engine.check`). `openSession` exists because visimer 1.1.4 throws on deleting a last-line node unless the source ends in a newline. Renaming previews: each keystroke redraws the diagram with the name so far (`VisualHost.preview`, never the document), so the node grows and the field is laid back over it — which is why the host has both `source()` (the document's) and `canvasSource()` (what is drawn). Selection chrome lives in an overlay beside the canvas; the selection's actions live in the block's bar, not in a floating toolbar, which in a laid-out diagram always covers a neighbour.
- *Text kits* (`textkit.ts`, `mindmap.ts`, `timeline.ts`, `gantt.ts`). A mind map, a timeline and a Gantt chart are not graphs, and visimer reads the first two only as lines (replace one, append one, delete one — it cannot say "an idea under this one"). Their kits read the source themselves and return text edits, which the session applies through visimer's `applyEdits` in place of a dispatched operation (`Op` is a record or a function). Three rules: an edit is the least text that says it (hosts merge the source as text — a status is a word, a shape two brackets, an added event a line of its own); an operation is compiled when it runs, against the source as it then is, from the entity's id alone; and an entity's id is its LINE (`idea:4`, `event:6:1`), since nothing else in these sources names a thing. That last one is why `VisualLayer.rebase` exists: whenever the document's source is not the one the held ids were read from, the selection and the idea being renamed are carried over the change by a line diff (`remapId`) — without it a line someone else adds above would silently make the selection another thing. `commitEdit` therefore finds its entity in the document's source at commit time, never in what the canvas last drew (which may be a preview of an older source). Pairing with Pele is by order for all three (two ideas can share their words; a timeline's events carry no id but are drawn inside their period), with any id that is written checked against the one drawn. A character a label's place cannot hold is written as its code (`#58;`) and shown decoded. Gantt: how many values a task has says what they are (end / start, end / id, start, end), so naming the task another comes after may give that task an id and a start; and Pele's `parse` does not read a chart's dates — `engine.check` asks the model for its tasks, or an unreadable start would be written and then fail to draw. Enter renames in every kind; "the next one beside it" (`DiagramKit.addAfter`) is Shift+Enter, on the canvas and in a name's field. A task's start and length are fields in the bar (`MermaidAction.field`), written on `blur` or Enter, each with a calendar where the chart's `dateFormat` is a plain day (`dayFormat` in `gantt.ts`: only `YYYY`, `MM`/`M`, `DD`/`D` and separators — anything else has no calendar) — the host's (`options.pickDate`), else the browser's, which needs a date field to own it (`nativeDate`: a 1px one, there while the picker is open); the bar is rebuilt on every change, so `renderBar` carries the focused control — and a field's typed text and caret — across the rebuild, after disarming the old field so that being removed does not make it write.
- *Specs run the real libraries* (`packages/mermaid/src/__tests__/`, run from that directory): the correlation rests on Pele's undocumented `data-id` values, so a Pele or visimer upgrade has to fail there rather than in a diagram. `boundary.spec.ts` holds the plugin to importing only `creo-edit`, `creo` and its two engines — in this repo a relative import into the editor's sources would compile and pass, and fail for everyone installing from npm. The browser-only behaviour (focus, dragging a connection, typing in a field inside the block) is in `examples/editor/tests/mermaid.spec.ts`; `examples/editor/?doc=diagram` opens on a diagram.

**Public API surface** is `src/index.ts` — anything exported there is part of the package contract; internal helpers should not be re-exported casually.
